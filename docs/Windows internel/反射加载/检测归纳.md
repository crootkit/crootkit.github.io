# CallStack

分两种情况，x86 和 x64.其中 64 bit 的程序的栈相对好获取。

## 64 bit

### 获取方式: ntdll.CaptureStackBackTrace

``` c
// ============================================================

// 方法一：CaptureStackBackTrace —— 最轻量，仅获取返回地址

// ============================================================

void Method1_CaptureStackBackTrace() {

    printf("\n========================================\n");

    printf("方法一：CaptureStackBackTrace\n");

    printf("========================================\n");

    printf("特点：无需初始化 DbgHelp，速度快，仅返回地址数组\n\n");

  

    #define MAX_FRAMES_M1 62

    PVOID backTrace[MAX_FRAMES_M1] = { 0 };

  

    // CaptureStackBackTrace 是 kernel32.dll 导出的 Win32 API，

    // 内部调用 ntdll!RtlCaptureStackBackTrace

    USHORT frames = CaptureStackBackTrace(

        0,               // FramesToSkip: 0 = 包含 CaptureStackBackTrace 自身

        MAX_FRAMES_M1,   // FramesToCapture: 最大帧数

        backTrace,       // 输出地址数组

        NULL             // BackTraceHash: 不需要则传 NULL

    );

  

    printf("捕获到 %hu 个栈帧:\n", frames);

    for (USHORT i = 0; i < frames; i++) {

        printf("  [%2hu]  0x%p\n", i, backTrace[i]);

  

        // 可选：尝试解析模块名（不依赖 SymInitialize）

        HMODULE hModule = NULL;

        if (GetModuleHandleExA(

                GET_MODULE_HANDLE_EX_FLAG_FROM_ADDRESS | GET_MODULE_HANDLE_EX_FLAG_UNCHANGED_REFCOUNT,

                (LPCSTR)backTrace[i],

                &hModule) && hModule)

        {

            char modulePath[MAX_PATH] = { 0 };

            GetModuleFileNameA(hModule, modulePath, sizeof(modulePath));

            const char *pName = strrchr(modulePath, '\\');

            const char *moduleName = pName ? (pName + 1) : modulePath;

            printf("        -> %s\n", moduleName);

        }

    }

}
```


### 获取原理 

```txt
① 读 .pdata    → 获取「这个函数的序言做了什么」
② 计算 RSP     → 逆向撤销序言操作，让 RSP 回到调用者的栈帧
③ 读返回地址   → *RSP 就是调用者中的返回地址，即调用者的 RIP
```

通过 IDA Pro 反编译 `ntdll.dll`，完整追踪了 [`RtlCaptureStackBackTrace`](vscode-webview://0ovrskb351lpn3d277spvijv0rrpp0v7m8gmojrvuklt1c725o07/index.html?id=fad0f184-bf0e-42aa-b5a6-8dbfdb81256a&parentId=3&origin=88b4c1a2-69ca-48dc-a325-25300df12832&swVersion=5&extensionId=ZooCodeOrganization.zoo-code&platform=electron&vscode-resource-base-authority=vscode-resource.vscode-cdn.net&parentOrigin=vscode-file%3A%2F%2Fvscode-app&purpose=webviewView#%E7%AC%AC%E4%B8%80%E5%B1%82rtlcapturestackbacktrace-0x1800526a0) 的内部实现链路：

```txt
用户调用 CaptureStackBackTrace(FramesToSkip=0, FramesToCapture=10, buf, NULL)
        │
        ▼
① RtlCaptureStackBackTrace
   └─ 参数校验 → 调用 RtlWalkFrameChain(buf, 11, 0x100)
        │
        ▼
② RtlWalkFrameChain

        │
        ▼
③ RtlpWalkFrameChain
   ├─ RtlpGetStackLimits()           ← 从 TEB 读 StackBase/StackLimit
   ├─ RtlpCaptureContext2()          ← 捕获当前 RIP/RSP/RBP/...
   │
   └─ 循环（每帧）:
       ├─ RtlpIsFrameInBounds()      ← RIP 在 [StackLimit, StackBase) 内？
       ├─ RtlpLookupFunctionEntryForStackWalks()  ← 二分查找 .pdata
       │   └─ RtlpxLookupFunctionTable() ← 查找模块函数表

       ├─ CET 返回地址修正            ← 处理控制流完整性保护
       └─ buf[frameCount-skip] = RIP ← 记录返回地址
        │
        ▼
④ 返回实际帧数给用户

```

 `RtlpxVirtualUnwind` @ [`0 x 180030 eb 0`] — 展开码解析引擎

这是最复杂的函数（0 x 5 E 9 字节），负责解析 `.pdata` 中的 **UNWIND_CODE** 序列：

1. **读取 UNWIND_INFO 头部**：确定展开码数量、序言/结尾大小、帧寄存器等
2. **解析执行 UNWIND_CODE 数组**：逆向执行函数序言中的指令，恢复调用者的寄存器值
3. **处理结尾（Epilogue）**：如果 RIP 在函数结尾中，直接从中恢复上下文
4. **更新 RSP**：恢复到调用者的栈指针位置
5. **恢复非易失寄存器**：从栈上恢复 rbx, rbp, rsi, rdi, r 12-r 15, xmm 6-xmm 15
6. **设置新的 RIP**：从栈上取出返回地址作为新的 RIP


**本质原理**：x 64 不依赖 RBP 链，而是通过 `.pdata` 段中的展开表 (`UNWIND_INFO` + `UNWIND_CODE[]`) 来精确恢复每一帧调用者的寄存器状态。这正是为什么必须使用 Windows API 而不能手动解析指针的原因——编译器可能完全省略帧指针，但展开表始终存在。

pdata 保存了什么, 只保存了函数序言和函数的地址范围，是静态的，编译的时候生成的。

```txt

                          .pdata 段（静态，每个函数一条）
                          ────────────────────────────

同一个函数被调用 10000 次:      ┌─────────────────────┐
                                │ RUNTIME_FUNCTION    │  ← 只有 1 条，与调用次数无关
  func_A() 被调用了:             │  for func_A         │
    第 1 次 ← call              │  BeginAddr = 0x1000 │
    第 2 次 ← call              │  EndAddr   = 0x1080 │
    第 3 次 ← call              │  UnwindInfo →       │
    ...                         ├─────────────────────┤
    第 10000 次 ← call          │ UNWIND_INFO         │
                                │  "这个函数序言中     │
  调用历史（次数/来源/参数）:    │   push了rbx, 分配了  │
    不在 .pdata 中！             │   0x20 字节栈空间"   │
    在运行时栈上！               └─────────────────────┘

```

#### 第一步：读 `.pdata` — [`RtlpLookupFunctionEntryForStackWalks`](vscode-webview://0ovrskb351lpn3d277spvijv0rrpp0v7m8gmojrvuklt1c725o07/index.html?id=fad0f184-bf0e-42aa-b5a6-8dbfdb81256a&parentId=3&origin=88b4c1a2-69ca-48dc-a325-25300df12832&swVersion=5&extensionId=ZooCodeOrganization.zoo-code&platform=electron&vscode-resource-base-authority=vscode-resource.vscode-cdn.net&parentOrigin=vscode-file%3A%2F%2Fvscode-app&purpose=webviewView)

```txt
当前 RIP = 0x7FF6...（在某个函数体内）
        │
        ▼
RtlpLookupFunctionEntryForStackWalks(RIP, &funcTableCtx)
        │
        ├─ 二分查找 .pdata 段
        │   ▸ 每个条目 12 字节: {BeginAddr, EndAddr, UnwindInfoRVA}
        │   ▸ 找到 RIP ∈ [BeginAddr, EndAddr) 的条目
        │
        └─ 返回 PRUNTIME_FUNCTION → UnwindInfoRVA → UNWIND_INFO
            └─ 包含 UNWIND_CODE[] 数组
```

#### 第二步：计算 RSP — [`RtlpxVirtualUnwind`](vscode-webview://0ovrskb351lpn3d277spvijv0rrpp0v7m8gmojrvuklt1c725o07/index.html?id=fad0f184-bf0e-42aa-b5a6-8dbfdb81256a&parentId=3&origin=88b4c1a2-69ca-48dc-a325-25300df12832&swVersion=5&extensionId=ZooCodeOrganization.zoo-code&platform=electron&vscode-resource-base-authority=vscode-resource.vscode-cdn.net&parentOrigin=vscode-file%3A%2F%2Fvscode-app&purpose=webviewView)

```c
// RtlpxVirtualUnwind 的核心逻辑（简化）
// 输入: funcEntry → UNWIND_INFO → UNWIND_CODE[]
// 输入: ctx->Rsp（当前函数的栈指针）

UNWIND_CODE codes[] = 从 .pdata 中读取;

for (每个 code in codes) {
    switch (code.OpCode) {
    case UWOP_PUSH_NONVOL:    // push rbx
        reg = *(PQWORD)ctx->Rsp;  // 从栈上读回 rbx 的原始值
        ctx->Rsp += 8;            // 撤销 push，RSP 上移
        break;

    case UWOP_ALLOC_SMALL:    // sub rsp, N*8
        ctx->Rsp += code.OpInfo * 8;  // 撤销栈分配
        break;

    case UWOP_ALLOC_LARGE:    // sub rsp, N
        ctx->Rsp += largeSize;       // 撤销大栈分配
        break;

    case UWOP_SET_FPREG:      // lea rbp, [rsp+offset]
        ctx->Rsp = ctx->Rbp - frameOffset;  // 从帧指针反算 RSP
        break;

    case UWOP_SAVE_NONVOL:    // mov [rsp+offset], reg
        regValue = *(PQWORD)(ctx->Rsp + code.Offset);
        set_register(code.Reg, regValue);
        break;
    }
}

// ★ 此时 ctx->Rsp 已经指向调用者的返回地址 ★
ctx->Rip = *(PQWORD)ctx->Rsp;   // 第三步：读返回地址
ctx->Rsp += 8;                   // RSP 指向调用者的栈帧
```

#### **引用链**

当 Windows 需要展开调用栈 (调试、异常处理等场景) 时，它会沿着可执行文件中内嵌的一条引用链逐级查找。

- **PE 头**
    
    中包含一个 DataDirectory 数组，其索引 3 的条目 (IMAGE_DIRECTORY_ENTRY_EXCEPTION) 存储了异常数据的 RVA 及大小，指向 .pdata 节。
    
- .pdata 节本质上是一个 RUNTIME_FUNCTION 结构数组，PE 中的每个函数对应一条记录。
    

```
typedefstruct _RUNTIME_FUNCTION {  DWORD BeginAddress;      // RVA where function starts  DWORD EndAddress;        // RVA where function ends  DWORD UnwindInfoAddress; // RVA of UNWIND_INFO structure} RUNTIME_FUNCTION;
```

- **UNWIND_INFO 结构**
存放在 .rdata 节中，精确描述了如何逆向执行每个函数的序言 (即编译器在函数入口处为设置栈和寄存器而生成的汇编指令)： 

``` c
typedefstruct _UNWIND_INFO {  
BYTE VersionAndFlags;        // Version (bits 0-2) and flags (bits 3-7)  BYTE SizeOfProlog;           // Size of prolog in bytes  
BYTE CountOfCodes;           // Number of unwind codes  BYTE FrameRegisterAndOffset; // Frame register info  
UNWIND_CODE UnwindCode[];    // Variable length array
} UNWIND_INFO;
```

#### **展开器的工作流程**

当 RtlVirtualUnwind 需要定位某个函数的调用者时，执行以下步骤：

- 获取当前指令指针 (RIP)
    
- 在 .pdata 中进行二分查找，找到包含该地址的 RUNTIME_FUNCTION 条目
    
- 根据 UnwindInfoAddress 在 .rdata 中定位对应的 UNWIND_INFO 结构
    
- 读取 UNWIND_CODE 数组，按逆序 "撤销" 函数序言——如果某个寄存器被压栈则弹出，如果分配了栈空间则将其加回 RSP
    
- 序言逆向执行完毕后，RSP 即指向返回地址
    
- 将返回地址弹入 RIP，然后重复上述过程
    

如此循环，直至 RIP 为 NULL 或指向内核空间，此时整个调用栈遍历完成。

#### 时机问题

**pdata:** 对于正常加载的可执行文件，Windows 在加载阶段就会解析并索引 .pdata 节。当 RtlLookupFunctionEntry 需要查找包含给定 RIP 的函数时，它查询的是操作系统加载器在映射 PE 时已注册的函数表，而非在展开过程中直接读取映像内存中的 .pdata。

**.rdata:** RtlVirtualUnwind 无法读取 UNWIND_INFO 结构来处理帧

## 二、ida 分析：Kernel 32.dll!HeapAlloc

``` c
DECLSPEC_ALLOCATOR LPVOID HeapAlloc(
  [in] HANDLE hHeap,
  [in] DWORD  dwFlags,// 
  [in] SIZE_T dwBytes
);
```

hHeap:
- 内存分配的堆的句柄。该句柄由 HeapCreate 或 GetProcessHeap 函数返回。

dwFlags:
- **HEAP_GENERATE_EXCEPTIONS**: 系统会触发异常以表示函数故障，例如内存不足状态，而不是返回 NULL。
- **HEAP_NO_SERIALIZE**: 串行访问不会用于此分配。
- **HEAP_ZERO_MEMORY**: 分配的内存将初始化为零。否则，内存不会初始化为零。

dwBytes:
- 分配字节数

如果函数成功，返回值将作为指向已分配内存块的指针。


注意：
- **HeapAlloc** 分配的内存不可移动。**HeapAlloc** 返回的地址在内存块被释放或重新分配之前有效;内存块不需要被锁定。由于系统无法压缩私有堆，它可能会变得碎片化。

### 2.2 底层实现

分析的目的是知道他如何从进程堆中扣一块下来，还是通过 virtualalloc 的套壳实现。

本质上调用的是：NTDLL.RtlAllocateHeap，重点分析这个的实现。


### 2.1 分配路径总览

RtlAllocateHeap() 根据堆签名分发，最终进入 RtlpAllocateHeapInternal()（地址 `0x18002aa20`，大小 `0xC20`，即 3104 字节的巨型函数）。该函数实现了**三级分配器**：

```txt
请求大小(size)
│
├─ size ≤ RtlpLargestLfhBlock (通常 0x4000 即 16KB)
│  └─ LFH (Low Fragmentation Heap) 路径
│     └─ RtlpLowFragHeapAllocFromContext() 或 RtlpHpLfhSlotAllocate()
│
├─ size ≤ 0x20000 (128KB)
│  └─ VS (Variable Size) 路径
│     └─ RtlpHpVsContextAllocateInternal()
│
└─ size > 0x20000 (128KB)
   ├─ size ≤ heap->SegmentSizeThreshold
   │  └─ Seg (Segment) 路径
   │     └─ RtlpHpSegAlloc()
   └─ size > SegmentSizeThreshold
      └─ Large 路径
         └─ RtlpHpLargeAlloc()
```

### 2.2 LFH 路径（小块分配 ≤ 16 KB）

LFH 是最常用的路径。在 [`RtlpAllocateHeapInternal()`](vscode-webview://0ovrskb351lpn3d277spvijv0rrpp0v7m8gmojrvuklt1c725o07/0x18002aa20) 中的关键逻辑：

```c
// 简化后的逻辑 (地址 0x18002ab6e 附近)
if (size <= RtlpLargestLfhBlock) {
    // 通过 bucket index map 找到对应的 bucket
    bucket_index = RtlpLfhBucketIndexMap[(actual_size + 15) >> 4];
    
    // 检查 bucket 是否激活
    if (heap->LfhBucket[bucket_index].Flags & 1) {
        // 尝试从 LFH context 分配
        result = RtlpLowFragHeapAllocFromContext(
            heap->LfhContext, 
            bucket->SlotCount,
            size, flags
        );
    }
    
    // 如果 LFH 失败，尝试激活 bucket 后重试
    if (result == -1) {
        RtlpHpLfhSlotAllocate(...);
    }
}
```

LFH 使用**预分配的 subsegment**（通常 64 KB），每个 subsegment 被划分为固定大小的 slot。分配时从 bitmap 中找到空闲 slot，O(1) 时间返回。

### 2.3 VS 路径（中等块 ≤ 128 KB）

```c
// 地址 0x18002ae59 附近
```

### 问题 1：如果要开辟的过大怎么解决

### 3.1 堆级大小限制检查

在 [`RtlpAllocateHeapInternal()`](vscode-webview://0ovrskb351lpn3d277spvijv0rrpp0v7m8gmojrvuklt1c725o07/0x18002aa20) 中有多层限制检查：

```c
// 1. 基本溢出检查 (地址 0x18002b289)
if (size > 0x7FFFFFFFFFFFFFFF) {
    // 立即失败，设置 LastError = ERROR_NOT_ENOUGH_MEMORY
    return NULL;
}

// 2. 堆级最大限制检查 (地址 0x18002b2a6)
max_size = heap->MaximumSize;  // 偏移 +392
if (!max_size) max_size = g_DefaultMaxHeapSize;  // 全局默认值
if (size > max_size) {
    RtlpLogHeapFailure(20, heap, ...);
    return NULL;
}

// 3. 全局内存限制检查 (地址 0x18002ab6e)
if (!g_IgnoreHeapLimit) {
    global_limit = heap->GlobalLimit;  // 偏移 +48
    if (!global_limit) global_limit = g_DefaultGlobalLimit;
    if (actual_size > global_limit) {
        RtlpLogHeapFailure(20, heap, ...);
        return NULL;
    }
}
```

### 问题 2：内存的权限是什么

### 4.1 保护级别

堆管理器使用两种保护级别，由 [`RtlpHpHeapValidateProtection()`](vscode-webview://0ovrskb351lpn3d277spvijv0rrpp0v7m8gmojrvuklt1c725o07/0x18000ee64) 确定：

```c
__int64 RtlpHpHeapValidateProtection(__int64 heap, unsigned int protection) {
    // 如果请求 PAGE_EXECUTE_READWRITE (0x40)
    if (protection == 0x40) {
        // 查询虚拟内存属性，确认确实是可执行的
        ZwQueryVirtualMemory(-1, heap, MemoryBasicInformation, ...);
        if (failed || !(basic_info.Protect & (PAGE_EXECUTE | PAGE_EXECUTE_READ))) {
            RtlpLogHeapFailure(0, heap, ...);
            return PAGE_READWRITE;  // 回退到普通保护
        }
    }
    return protection;
}
```

**两种保护级别**：

| 堆标志                          | 保护值                             | 含义       |
| ---------------------------- | ------------------------------- | -------- |
| 默认                           | `0x04` (PAGE_READWRITE)         | 可读写，不可执行 |
| `HEAP_CREATE_ENABLE_EXECUTE` | `0x40` (PAGE_EXECUTE_READWRITE) | 可读写，可执行  |
注：HEAP_CREATE_ENABLE_EXECUTE 属性的堆不受 DEP （NX）保护
### 4.2 保护标志的传递路径

```txt
RtlAllocateHeap(heap, flags, size)
  → RtlpAllocateHeapInternal(heap, size, heap_flags, ...)
    → RtlpHpHeapValidateProtection(heap, heap->Flags & HEAP_CREATE_ENABLE_EXECUTE ? 0x40 : 0x04)
      → RtlpHpAllocVA(..., protection, ...)
        → NtAllocateVirtualMemoryEx(..., protection, ...)
```

### 问题 3：为什么无法 protect 上可执行权限

这是最关键的问题。根据对代码的深入分析，有以下几个原因：

### 5.1 堆管理器内部状态与外部修改不同步

堆管理器在分配/释放/重分配时会**验证内存的保护属性**。当你用 `VirtualProtect` 外部修改保护后，堆管理器的内部状态与实际不一致：

```c
// RtlpHpHeapValidateProtection 在每次 commit 操作时被调用
// 它会查询实际的虚拟内存保护属性
// 如果发现与预期不符，会回退到 PAGE_READWRITE
```

### 5.2 VS Subsegment 的保护验证

在 [`RtlpHpVsSubsegmentCreate()`](vscode-webview://0ovrskb351lpn3d277spvijv0rrpp0v7m8gmojrvuklt1c725o07/0x180072268) 中，subsegment 创建时会记录保护类型。后续的 chunk 分裂/合并操作依赖这个保护类型：

```c
// subsegment 创建时记录保护 (地址 0x180072304)
if (alloc_info.Protect & PAGE_EXECUTE) {
    commit_size = alloc_size;  // 可执行页整块提交
}
```

如果外部修改了保护，chunk 分裂时的保护验证会失败。

### 5.3 Segment PageRange 的保护验证

在 [`RtlpHpSegPageRangeCommit()`](vscode-webview://0ovrskb351lpn3d277spvijv0rrpp0v7m8gmojrvuklt1c725o07/0x180023180) 中，commit 操作会调用 `RtlpHpSegMgrCommit()`，后者会：

```c
// 地址 0x180022f89
v22 = (*(_DWORD *)(heap + 20) & 0x40000000) != 0;
protection = RtlpHpHeapValidateProtection(heap, v22 ? 0x40 : 0x04);
// 如果实际保护与预期不符，返回 0x04 (PAGE_READWRITE)
```

这意味着如果你用 `VirtualProtect` 把堆内存改成可执行，后续的 commit 操作会：

1. 查询到实际保护是 `PAGE_EXECUTE_READWRITE`
2. 但堆管理器预期的是 `PAGE_READWRITE`
3. 触发 `RtlpLogHeapFailure(0, ...)` 记录堆失败
4. 回退到 `PAGE_READWRITE`，**覆盖掉你设置的可执行权限**

### 5.4 堆完整性检查 (Heap Integrity Checks)

堆管理器在分配和释放时进行多种完整性检查：

```c
// 堆段描述符验证 (地址 0x18002b003)
if ((RtlpHpHeapGlobals ^ segment_addr ^ (segment_addr & mask) ^ *(segment_addr + 0x10)) 
    != 0xA2E64EADA2E64EAD) {
    // 段描述符损坏
    return 0;
}
```

如果外部修改保护导致内存布局变化，这些检查可能失败，触发 `__fastfail(3)` (HEAP_CORRUPTION) 终止进程。

### 5.5 正确的做法

**要获取可执行堆内存，必须在创建堆时指定标志**：

```c
// 方法1: 创建可执行堆
HANDLE hHeap = HeapCreate(HEAP_CREATE_ENABLE_EXECUTE, 0, 0);
void* ptr = HeapAlloc(hHeap, 0, size);

// 方法2: 直接使用 VirtualAlloc
void* ptr = VirtualAlloc(NULL, size, MEM_COMMIT | MEM_RESERVE, 
                         PAGE_EXECUTE_READWRITE);
```

使用 `HEAP_CREATE_ENABLE_EXECUTE` 创建的堆，其内部所有路径（LFH/VS/Seg/Large）都会使用 `PAGE_EXECUTE_READWRITE` 保护，堆管理器的内部状态与实际保护一致，不会出现上述问题。

### 总结

1、可以使用 heapalloc 来开辟一段可执行的 heap 内存。
2、针对 rwx 的内存地址，heap 和 virtualalloc 的底层都是通过 ntvirtualallocmemory 实现的。
3、差异（检测依据）
- **内存结构差异：** heap 类型的地址中存在 heap 结构，shellcode 在 heap 中并不是从头开始的。但是 virtualalloc 就是一段纯净的空间。
- **属性差异：** 属性基本没有差异，仅有上面的数据格式差异。
- **callstack 差异**：这才是真正能用的差异，差点忘了。根据 callstack 中是否存在 heapalloc 来判断到底是 virtualalloc 还是 heapalloc。

4、所以，目前采集到的 virtualalloc 事件是无法区分 heap 开辟还是手动开辟的。

### **总结**


ntallocvirtualmemory 事件，我们根据两种不同的方式（开辟堆、直接申请内存），分析出了针对两种方式的过滤条件：

#### **heap**

通过分析发现，alloc 的 ti 事件，很多是由开辟堆的行为产生的，所以要通过 callstack 对开辟堆行为的 alloc 事件进行过滤。（堆的地址属性和 virtualalloc 出的地址属性并无差异，无法通过 query 方法辨别，这里只能使用 callstack）。

堆开辟又有两种情况，heapcreate 和 heapalloc。
- heapalloc：必须有堆对象的句柄才能进行 alloc；当 alloc 地址过大的时候，也会产生 alloc 的 ti 事件。
- heapcreate：创建一个指定权限的内存地址(默认 0 x 2000)，一定会产生 alloc 的 ti 事件。
而且根据 Windows 的系统机制：Windows DEP 保护默认堆栈不可执行，所以一般进程不会开辟 RWX 的 stack。为了在堆上执行代码，必须手动进行 heapcreate，开辟一段 RWX 属性的堆地址。

所以，我们只需要关注从 unbacked 地址开辟 RWX 的栈行为即可。过滤策略（AND 关系）：
- 通过 callstack 中的 api 名称进行过滤。只保留存在 createheap 字段的即可。
- 开辟的地址属性是 RWX 的。
- callstack 中存在 unbacked 的。

#### **virtualalloc**

callstack 中，没有堆特征的调用事件，被认为是直接调用 virtualalloc。针对此类事件，采用下面的过滤方式（和 createthread 事件的过滤策略类似）（AND 关系）
- 开辟的地址属性是 RWX 的。
- callstack 中存在 unbacked 的。

经过 python 测试，会产生很多 virtualalloc 事件，但是目标权限都是 RW，除非代码中调用，几乎没有可执行的地址开辟事件。
