# 分析思路
## 第一阶段：入口点分析（Loader）

**起点**：从用户态可执行文件开始，这是整个作弊部署流程的初始环节。

**分析重点**：

- 反取证机制：每次使用唯一哈希、执行后自删除
- 通信安全：JWT 认证、HTTPS 传输、自定义对称加密（前 16 字节作为密钥）
- 持久化机制：挂载 EFI 系统分区，替换 bootmgfw.efi 和 bootx 64.efi
- 载荷投递：在 bootloader 中追加包含 JWT、目标进程名、加密作弊二进制的段

**思路逻辑**：先理解攻击者如何进入系统并建立持久化，这是后续所有分析的基础。

## 第二阶段：固件层分析（Bootloader Implant）

**切入点**：分析被 Themida 保护的 UEFI 植入物。

**分析步骤**：

1. **去混淆**：处理 Themida 的虚拟机保护、压缩和多段加密
2. **执行流程还原**：
    - 入口点恢复原始 bootmgfw.efi/bootx 64.efi
    - 时间戳伪造（从 bootmgr.efi 窃取微软原始时间戳）
    - 反虚拟化检测（CPUID + RDTSC/RDTSCP 时序检查）
    - SetVirtualAddressMap 钩子安装
3. **关键函数逆向**：
    - `UpdateTimestampsRecursive`：递归更新时间戳以规避检测
    - `RestoreBootManager`：从备份恢复原始文件
    - `Phase0_AllocateAndInitialize_TwoMemoryPools`：分配 20 MB 和 80 MB 内存池

**思路逻辑**：固件层是攻击链的关键转折点——在这里植入物获得了操作系统加载前的控制权，为后续注入 Hypervisor 铺平道路。

## 第三阶段：操作系统加载器劫持（SetVirtualAddressMap Hook）

**分析焦点**：理解植入物如何从固件层过渡到操作系统层。

**技术细节**：

- SetVirtualAddressMap 在 winload 调用 ExitBootServices 后被触发
- 植入物通过返回地址回溯找到 winload 的镜像基址
- 对 winload 进行特征码扫描，定位 hvloader 基址和上下文切换函数
- 最终找到 Hyper-V 的初始化入口

**思路逻辑**：这是连接固件层和 Hypervisor 层的桥梁。通过 hook 这个关键函数，植入物能够在操作系统建立虚拟地址映射时介入，为后续注入 Hyper-V 做准备。

## 第四阶段：Hypervisor 注入与内存操控

**分析内容**：

1. **Hyper-V 注入**：如何将代码映射到 Hyper-V 空间
2. **SLAT 逻辑**：二级地址转换的实现方式
3. **客户物理内存重定向**：
    - EPT 违规处理：当客户机访问被 hook 的页面时触发
    - MTF 处理：单步执行机制用于精细控制

**思路逻辑**：这一层是整个架构的核心——通过控制 Hypervisor，ring-1.io 能够在客户操作系统完全不知情的情况下操控内存和执行流。

## 第五阶段：进程注入机制

**分析步骤**：

1. **页表克隆**：复制目标游戏的 PML 4 页表
2. **恶意页表项插入**：在克隆的页表中添加指向作弊 DLL 的条目
3. **页表加载**：通过 Hypervisor 调用加载修改后的页表
4. **隐藏机制**：
    - 隐藏恶意页表本身
    - 通过 EPT 隐藏内存内容（使用 0 xCE 填充不可见页面）

**思路逻辑**：这是作弊代码实际进入游戏进程的方式。通过页表克隆而非传统的内存分配，可以规避常规的内存扫描检测。

## 第六阶段：EPT 钩子机制

**分析内容**：两种不同的 EPT 钩子实现：

1. **内联重定位钩子**：
    - 修改目标函数前几条指令为 JMP
    - 被覆盖的指令复制到 trampoline
    - 适用于函数入口点
2. **全上下文 Shellcode 钩子**：
    - 在任意指令边界（包括函数中间）插入 14 字节绝对 JMP
    - 跳转到保存完整 CPU 状态的 shellcode
    - 不依赖调用约定或寄存器使用情况
    - 适用于更复杂的 hook 场景

**分析细节**：

- 通过修改 EPT 执行权限实现隐蔽修改
- Shellcode 保存所有通用寄存器、FPU/SSE 状态
- 使用魔术值（0 x 1 E 38 EDFF 2301 EEBC）定位并替换回调函数地址

**思路逻辑**：EPT 钩子是 ring-1.io 实现各种功能的核心机制，理解这两种实现方式对于理解后续所有 hook 的功能至关重要。

## 第七阶段：具体 Hook 功能分析

**分析方法**：对每个安装的 hook 进行功能逆向：

|Hook 目标|功能|
|---|---|
|**nvlddmkm.sys**|拦截 GID 验证/提取，用于硬件 ID 欺骗|
|**KiDispatchException**|为植入物提供自定义异常处理，安全执行不安全的内存读写|
|**KiSystemCall 64_ServiceExit**|绕过 Windows 检测回调，隐藏直接系统调用|
|**NtGdiBitBlt/StretchBlt**|拦截截图操作，通知用户态进行反截图处理|
|**PsWatchWorkingSet**|抑制工作集监控，隐藏植入物的内存访问|

**分析细节**（以 KiDispatchException 为例）：

- 植入物在执行不安全内存操作前，将魔术值 0 x 9 EFABE 87 C 1 FE 38 E 2 放入 r 10
- 如果发生异常，hook 检查故障 RIP 是否在植入物范围内
- 如果是预期异常，将 r 10 改为 0 x 1337 作为失败信号
- 推进 RIP 跳过故障指令，防止重复执行
- 非植入物范围的异常正常传递给内核处理

**思路逻辑**：从通用机制到具体应用，理解每个 hook 如何解决特定的技术挑战（如反检测、反截图、异常处理等）。

## 第八阶段：通信机制分析

**分析内容**：

- **用户态 → 内核态**：通过共享通信块传递数据
- **内核态 → VMX-root**：通过 VMCALL 或其他机制与 Hypervisor 通信

**思路逻辑**：理解不同权限层级之间如何协作，这是理解整个系统架构的关键。

## 第九阶段：检测策略推导

**分析方法**：基于前述分析中发现的实现弱点，反向推导检测方法：

1. **Shadow PML 4 E 扫描**：
    - 发现：植入物克隆 PML 4 但在同步时会跳过自己的条目
    - 推导：在克隆的 CR 3 上下文中探测，找到没有对应 VAD 的内存区域
2. **IPT 分析**：
    - 发现：作弊 DLL 的地址在真实页表中没有映射
    - 推导：启用 IPT 后，IP 包会暴露这些地址，PIP 包会暴露克隆的 CR 3
3. **0 xCE 页面扫描**：
    - 发现：EPT 隐藏页面使用 0 xCE 填充
    - 推导：扫描物理内存中的全 0 xCE 页面
4. **EFI 运行时执行分析**：
    - 发现：植入物代码映射到 EFI 运行时区域
    - 推导：标记为 NX 后通过页面故障识别活跃执行页面
5. **Hyper-V 内存暴露**：
    - 发现：SLAT 实现没有保护 Hyper-V 内存
    - 推导：通过修改 CPUID 厂商字符串验证是否能访问真实 Hyper-V
6. **RWX 异常**：
    - 发现：EPT 重建为 RWX 权限的身份映射
    - 推导：在 HVCI 系统上这违反了 W^X 语义

**思路逻辑**：这是分析的最终产出——将逆向工程的发现转化为可操作的防御策略。作者强调这些检测应该在服务端进行分类，因为客户端不可信。

## 贯穿始终的分析原则

1. **分层递进**：从用户态到固件态到 Hypervisor 到内核态，逐层深入
2. **代码级验证**：不仅描述行为，还还原关键函数的伪代码和汇编
3. **攻防对应**：每发现一种攻击机制，就思考对应的检测方法
4. **系统性思维**：不孤立地看待单个技术，而是理解整个架构的设计哲学

# 一、加载器
## 1.1 行为
- 该加载器作为 ring-1.io 作弊部署流水线中的初始用户模式可执行文件。该加载器设计用于规避，每个加载器实例拥有独特的文件哈希值，执行后会自动删除。
- 防止被上传沙箱吧，或者是为了减少暴露面，或者是为了更好的收费。

## 1.2 加载过程

文件替换：
- 加载器会挂载 EFI 系统分区，并用修改版本替换磁盘上的 bootmgfw.efi 和 bootx 64.efi。
- 每选定一个作弊，都会在引导加载程序植入物中附加一个额外部分。这些部分包含用户的 JWT 令牌、目标进程名称以及加密的游戏作弊的代码。

启动过程：
本质是劫持了驱动组件的加载顺序。
- 在下一次系统启动时，修改后的 bootmgfw.efi 或 bootx 64.efi 在操作系统加载前执行，从而赋予植入体对启动过程的完全控制权。
- 引导加载程序的入口被绕道到一个名为.trp 的附加部分。
植入入口点执行后，控制权会返回 bootmgfw.efi 或 bootx 64.efi 的原始入口点。这些修改本质上违反了安全启动的完整性。因此不支持安全启动。

在执行真实入口点后，植入物会立即恢复 EFI 系统分区上的原始 bootmgfw.efi 和 bootx 64.efi 二进制文件。然后它会操控这些文件和父文件夹的最后修改时间，试图规避检测。
