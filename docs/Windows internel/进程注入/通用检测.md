# 进程创建 suspend 检测

## 难点

suspend 标志位，并不在进程创建回调的 _PS_CREATE_NOTIFY_INFO 结构体中
```
typedef struct _PS_CREATE_NOTIFY_INFO {
    _In_ SIZE_T Size;
    union {
        _In_ ULONG Flags;
        struct {
            _In_ ULONG FileOpenNameAvailable : 1;
            _In_ ULONG IsSubsystemProcess : 1;
            _In_ ULONG Reserved : 30;
        };
    };
    _In_ HANDLE ParentProcessId;
    _In_ CLIENT_ID CreatingThreadId;
    _Inout_ struct _FILE_OBJECT *FileObject;
    _In_ PCUNICODE_STRING ImageFileName;
    _In_opt_ PCUNICODE_STRING CommandLine;
    _Inout_ NTSTATUS CreationStatus;
} PS_CREATE_NOTIFY_INFO, *PPS_CREATE_NOTIFY_INFO;
```

也不在 Microsoft-Windows-Kernel-Process 这个 ETW 事件中。所以并不是一个 Windows 格式化的采集标志字段。

## 必要性

1、很多 hollowing、劫持、早期的回调攻击，都是利用了创建 suspend 进程的特性来工作的。

2、通过增加这个采集，可以提高像线程劫持等 POC 的精准检出，比如 cs 的 spwanto 命令等。

其他未知手法的检出。

## 采集

9.1.2 版本的 elastic 的规则中存在这个标志位，所以对 es 的组件进行了逆向分析。
### R 3

首先是用户态，通过逆向发现，他是对驱动上报的一些字段进行判断，然后决定是否给目标进程添加 suspend_create 这个标记的，核心还是来源于驱动上报的信息。
``` c
sub_140008BF0(..., v72, ...);
// 通过 FltSendMessage 发送，魔数 0x90000002
// v72 写入消息偏移 4328
```

然后就是值判断逻辑, 这里的判断值是未经操作的，是采集到的原始的值。

``` c
// 读取 [rsi+10D8h] = v72（驱动发送的栈数据）

if (v72 == 0x10000000)           → 不标记（默认值/未获取到）
if ((v72 & 0x202) == 0x200)     → 不标记（CREATE_NEW_PROCESS_GROUP 模式）
否则                              → ProcessEvent::CreatedSuspended = true
```

#### 分析

用户态定位后，来到驱动中，按照用户态的数据来源，和驱动中，进程创建回调函数，交叉定位到 suspend 标志位采集的功能函数。

通过前置条件判断（全局标志位检查），定位到和进程创建检查相关的结构：

`sub_1400158E0` 函数实现了 suspend 标志位的具体遥测思路。
``` c
sub_1400158E0(outputBuffer):
{
    // 3a. 分配 CONTEXT 缓冲区
    //     通过 KeStackAttachProcess + ZwAllocateVirtualMemory
    //     在当前进程地址空间分配 0x4D0 (1232) 字节
    
    // 3b. 设置 ContextFlags = 0x100003
    //     = CONTEXT_AMD64 | CONTEXT_CONTROL | CONTEXT_INTEGER
    
    // 3c. PsGetContextThread(KeGetCurrentThread(), ctx, UserMode)
    //     获取创建线程的用户态上下文（SYSCALL 入口时的状态）
    
    // 3d. 安全验证：*(WORD*)(Rip - 2) == 0x050F (SYSCALL 指令)
    //     确认线程确实在系统调用入口点
    
    // 3e. 读取寄存器值：
    //     outputBuffer[96] = Rax 低32位 → v115（系统调用号）
    //     outputBuffer[0]  = Rcx
    //     outputBuffer[8]  = Rdx
    
    // 3f. 读取用户态栈数据：
    //     outputBuffer[48] = Stack[Rsp+56] (16字节 OWORD) → v112
}
```

#### 逻辑复现

先不要陷入分析，llm 的分析未必正确，我们先来观察这个值是否存在一定的规律。

``` c
/* ES 使用 0x100003 = CONTEXT_AMD64 | CONTEXT_CONTROL | CONTEXT_INTEGER */
pCtx->ContextFlags = 0x100003;

currentThread = PsGetCurrentThread();

DbgPrint("[SUSPEND_CHECK] Calling PsGetContextThread(%p, %p, UserMode)...\n", currentThread, pCtx);
status = g_pPsGetContextThread(currentThread, pCtx, UserMode);
if (!NT_SUCCESS(status)) {
    DbgPrint("[SUSPEND_CHECK] PsGetContextThread(UserMode) failed: 0x%08X\n", status);
}
else {
    ULONG64 rip = pCtx->Rip;
    ULONG64 rsp = pCtx->Rsp;
    ULONG64 rax = pCtx->Rax;

    DbgPrint("[SUSPEND_CHECK] ========== Thread Context ==========\n");
    DbgPrint("[SUSPEND_CHECK] RIP = 0x%llX\n", rip);
    DbgPrint("[SUSPEND_CHECK] RSP = 0x%llX\n", rsp);
    DbgPrint("[SUSPEND_CHECK] RAX = 0x%llX  (syscall number)\n", rax);
    DbgPrint("[SUSPEND_CHECK] RCX = 0x%llX\n", pCtx->Rcx);
    DbgPrint("[SUSPEND_CHECK] RDX = 0x%llX\n", pCtx->Rdx);
    DbgPrint("[SUSPEND_CHECK] R8  = 0x%llX\n", pCtx->R8);
    DbgPrint("[SUSPEND_CHECK] R9  = 0x%llX\n", pCtx->R9);

    /* 验证 RIP-2 处是否为 SYSCALL 指令 (0x0F 0x05) */
    __try {
        ProbeForRead((PVOID)(rip - 2), 2, 1);
        USHORT syscallOpcode = *(USHORT*)(rip - 2);
        DbgPrint("[SUSPEND_CHECK] *(WORD*)(RIP-2) = 0x%04X (expected 0x050F = SYSCALL)\n", syscallOpcode);

        if (syscallOpcode != 0x050F) {
            DbgPrint("[SUSPEND_CHECK] Not at SYSCALL entry point\n");
        }
        else {
            /* 读取用户态栈上的 NtCreateUserProcess 参数 */
            ProbeForRead((PVOID)(rsp), 0x60, 1);

            /*
             * 参考 ES 驱动的实际逻辑：
             * 1. 从 ntdll 导出表解析 NtCreateUserProcess 的系统调用号
             * 2. 比较 Rax 是否等于该系统调用号
             * 3. 如果匹配，读取栈数据 Rsp+56（0x38）
             * 4. 使用排除法判断：如果栈数据不匹配已知的"非挂起"模式，则标记为 suspended
             *
             * ES 驱动的排除逻辑（用户态 sub_1403DD450）：
             *   if (v72 == 0x10000000) → 不标记（默认值/非系统调用）
             *   if ((v72 & 0x202) == 0x200) → 不标记（CREATE_NEW_PROCESS_GROUP 模式）
             *   否则 → 标记 created_suspended = true
             */
            ULONG64 stackVal = *(ULONG64*)(rsp + 0x38);
            DbgPrint("[SUSPEND_CHECK] [Rsp+0x38] = 0x%016llX\n", stackVal & 0xFFFFFFFF);

            /* Dump 完整栈 */
            DbgPrint("[SUSPEND_CHECK] ========== Stack Dump ==========\n");
            for (int i = 0; i <= 0x80; i += 8) {
                DbgPrint("[SUSPEND_CHECK] [Rsp+0x%03X] = 0x%016llX\n", i, (*(ULONG64*)(rsp + i)) & 0xFFFFFFFF);
            }

            /* 应用 ES 驱动的判断逻辑 */
            ULONG32 v72 = (ULONG32)(stackVal & 0xFFFFFFFF);
            DbgPrint("[SUSPEND_CHECK] v72 (stack value) = 0x%08X\n", v72);

            if (v72 == 0x10000000) {
                DbgPrint("[SUSPEND_CHECK] v72 == 0x10000000 → skip (default/not syscall)\n");
            }
            else if ((v72 & 0x202) == 0x200) {
                DbgPrint("[SUSPEND_CHECK] (v72 & 0x202) == 0x200 → skip (CREATE_NEW_PROCESS_GROUP)\n");
            }
            else {
                DbgPrint("[SUSPEND_CHECK] ★★★ PID=%lu: created_suspended = TRUE ★★★\n", HandleToULong(ProcessId));
                result = TRUE;
            }
        }
    }
    __except (EXCEPTION_EXECUTE_HANDLER) {
        DbgPrint("[SUSPEND_CHECK] Exception during stack analysis\n");
    }
}
```

### 逻辑分析

现在的问题是：为什么在陷入 syscall 之后，用户态的当前线程的 `rsp+0x38` 的位置处的值可以进行判断。

**1、用户态 callstack 逻辑变更调试：**

目的：定位在哪一个层级的调用的时候，会导致 `rsp+0x38` 的值变化为最终值。

1.1 猜测规律 
- 创建 suspend 进程，到 syscall 执行，这值是 0。
- 创建正常进程，到 syscall 执行，这个值是 `0x200`。
经过测试，决定使用正常的进程创建来分析，因为 0 太常见了。

1.2 定位变化层级
- 定位 callstack 上一级跳转，去栈中找这个值，发现在 `rsp+0x30` 的位置，符合预期（call 的话要 push 返回地址，导致栈+8，后面的偏移都需要后移 8）
- 定位callstack 上一级跳转的上一级跳转，发现附近的栈中不存在 `0x200`。

结论：认定该 `rsp+0x38` 值的产生，在 syscall 的上第二级函数中，也就是 `CreateProcessInternalW` 中。

**2、静态分析该值产生逻辑**

确定了在跳入 syscall 之前，该值在栈中的位置是  `rsp+0x30` 所以，ida 分析 `kernelbase. CreateProcessInternalW` 这个函数中，对 `rsp+0x30` 值的修改即可。

### 3.1 阶段一：初始标志位运算（`0x180041a2f` ~ `0x180041a75`）

反编译代码：

```c
// Step 1: 掩码过滤 dwCreationFlags
// 掩码 0xFFFF3E1F 清除的位: bit5(0x20), bit6(0x40), bit7(0x80), bit8(0x100),
//                           bit13(0x2000), bit14(0x4000), bit15(0x8000)
// ★ bit2 (0x4=CREATE_SUSPENDED) 被保留！
v18 = dwCreationFlags & 0xFFFF3E1F;
v179 = v18;  // 存储到局部变量

// Step 2: 基础标志
// 如果 dwCreationFlags & 0x1000 → bit6 = 0x40
// 默认 bit0 = 1，除非 dwCreationFlags & 0x1000000
v19 = (v18 >> 12) & 0x40 | 1;
if ((v18 & 0x1000000) == 0)
    v19 = (v18 >> 12) & 0x40;

// Step 3: EXTENDED_STARTUPINFO 相关标志
v20 = v19 | 0x100;     // bit8 = 0x100
if ((v18 & 0x10000) == 0)
    v20 = v19;         // 清除 bit8

// ★ Step 4: CREATE_NEW_PROCESS_GROUP vs CREATE_SUSPENDED (关键!)
v21 = v20 | 0x200;     // BTS ebx, 9 → bit9 = 0x200
if ((v18 & 4) != 0)    // AND al, 4 → 检查原始 dwCreationFlags 的 CREATE_SUSPENDED
    v21 = v20;         // CMOVNZ → 有挂起标志则移除 0x200
v198 = v21;            // mov [rsp+0xF4], ebx
```

等价伪代码：

```c
v198 = base_flags;                    // 从 dwCreationFlags 派生（bit0, bit6, bit8）
v198 |= 0x200;                        // 默认添加 CREATE_NEW_PROCESS_GROUP
if (dwCreationFlags & CREATE_SUSPENDED)
    v198 = base_flags;                // 挂起时：移除 CREATE_NEW_PROCESS_GROUP
```

### 3.2 阶段二：调试标志（[`0x180041ac4`](kernelbase.dll:0x180041ac4)）

``` asm
; 0x180041ab7 - 0x180041ac4
test    byte ptr [rsp+1568h+v179_dwCreationFlags], r13b  ; r13b = 2
jz      short loc_180041AD5
or      ebx, r13d                                        ; v198 |= 0x2 (DEBUG_ONLY_THIS_PROCESS)
```

**触发条件**：`dwCreationFlags & DEBUG_ONLY_THIS_PROCESS (0x2)` 或调试相关标志。

### 3.3 阶段三：属性列表标志（[`0x180041f7c`](kernelbase.dll:0x180041f7c)）

``` asm
; 0x180041f72 - 0x180041f7c
test    byte ptr [rsp+1568h+var_1390], 4   ; 检查 v236 & 4
jz      short loc_180041F85
bts     [rsp+1568h+var_1474], 0Ah          ; v198 |= 0x400 (bit10)
```

**触发条件**：`BasepConvertWin32AttributeList` 返回的 `v236` 中 bit 2 被设置。来自 `STARTUPINFOEX` 的 `PROC_THREAD_ATTRIBUTE_LIST`。

### 3.4 阶段四：AppX 上下文标志（[`0x1800430f8`](kernelbase.dll:0x1800430f8)）

``` asm
; 0x1800430f8
or      [rsp+1568h+var_1474], 40h   ; v198 |= 0x40 (bit6)
```

**触发条件**：`v208`（AppX 上下文字段）存在且 `(v208 + 80) & 1` 时。UWP/AppContainer 进程的激活路径。

### 3.5 阶段五：InheritHandles（[`0x18004310f`](kernelbase.dll:0x18004310f) ~ [`0x18004311b`](kernelbase.dll:0x18004311b)）

``` asm
; 0x180043108 - 0x18004311b
cmp     [rsp+1568h+arg_28], edi           ; 比较 a6 (bInheritHandles) 与 0
jz      short loc_18004311B
or      [rsp+1568h+var_1474], 4           ; a6=TRUE  → v198 |= 0x4
jmp     short loc_180043123
and     [rsp+1568h+var_1474], 0FFFFFFFBh  ; a6=FALSE → v198 &= ~0x4
```

**触发条件**：`CreateProcess` 的第 5 参数 `bInheritHandles`。

### 总结 

#### 常规情况

| 位     | 掩码                 | 来源阶段  | 含义                                   | 触发条件                                                |
| ----- | ------------------ | ----- | ------------------------------------ | --------------------------------------------------- |
| 0     | `0x00000001`       | 阶段一   | 启动信息扩展标志                             | `dwCreationFlags & 0x1000000`                       |
| 1     | `0x00000002`       | 阶段二   | 调试标志                                 | `dwCreationFlags & DEBUG_ONLY_THIS_PROCESS` (0 x 2) |
| **2** | ** `0x00000004` ** | 阶段五   | **bInheritHandles**                  | `CreateProcess` 第 5 参数为 TRUE                        |
| **6** | ** `0x00000040` ** | 阶段一/四 | **CHECK_UNICODE_ENV** 或 **AppX 上下文** | `dwCreationFlags & 0x1000` 或 UWP 进程激活               |
| 8     | `0x00000100`       | 阶段一   | 扩展启动信息存在                             | `dwCreationFlags & 0x10000`                         |
| **9** | ** `0x00000200` ** | 阶段一   | **CREATE_NEW_PROCESS_GROUP**         | 正常创建自动添加，挂起创建自动移除                                   |
| 10    | `0x00000400`       | 阶段三   | 属性列表扩展标志                             | `PROC_THREAD_ATTRIBUTE_LIST` 中特定标志被设置               |

下面是 es 针对上述遥测值进行的匹配情况

| 实测值          | `& 0x202` | `== 0x200`? | ES 判断            | 是否正确         |
| ------------ | --------- | ----------- | ---------------- | ------------ |
| `0x00000000` | `0x000`   | ❌           | **标记 suspended** | ✅ (挂起)       |
| `0x00000004` | `0x000`   | ❌           | **标记 suspended** | ✅ (挂起+继承句柄)  |

| `0x00000204` | `0x200`   | ✅           | 不标记              | ✅ (正常+继承句柄)  |

| `0x00000604` | `0x200`   | ✅           | 不标记              | ✅ (正常+继承+属性) |
